Format: `ADR-N · date · decision · why · alternatives rejected`

- **ADR-5 · 2026-07-24 · Groups deferred to Phase 3 (Stage 1).** MVP must prove public layer + moderation spine first. _Rejected:_ groups-in-MVP (empty infiltration-prone shells).
- **ADR-6 · 2026-07-24 · Add-by-user-ID preferred over phone number.** Contact discovery leaks who uses a protest app. _Rejected as default:_ phone adding (kept as opt-in, hidden numbers).
- **ADR-7 · 2026-07-24 · flutter_map + OSM + FMTC over Google Maps.** Offline tile caching, no billing/quota, no Google dependency. _Rejected:_ google_maps_flutter (weak offline), Mapbox (cost).

FCM may still be used later for push only. _Rejected:_ Firebase (weaker relational authz, no self-host, full Google dependency).
- **ADR-9 · 2026-07-24 · Glassmorphism UI (hero surfaces only) + neutral/one-accent palette + rich animations.** User's style choice; performance guarded by device-tier fallback (no blur on weak devices), reduced-motion/battery mode, and a no-glass high-contrast outdoor theme. _Rejected:_ app-wide glass (GPU cost on <2GB-RAM Androids).
- **ADR-10 · 2026-07-24 · Accent = Saffron `#FF6D1F`; dark mode follows system.** User's choice, made aware of the flagged trade-offs (proximity to amber "Low" status color; cultural/political connotation). Mitigations: accent is NEVER used to convey facility status (status = own semantic color + icon + text, enforced via `StatusColors` ThemeExtension outside the seed scheme); CVD-simulator audit each release stays mandatory. System-follow theme with manual Light/Dark/Outdoor override in settings. _Rejected:_ indigo/teal (user preference), light-default (ignores OS preference, loses OLED battery savings).
- **ADR-11 · 2026-07-24 · Monorepo layout: docs at root, Flutter app in `app/`, backend-as-code in `supabase/` (later).** Keeps RLS policies/migrations version-controlled next to the app for auditable security review; CI uses `working-directory: app`. _Rejected:_ Flutter at repo root (crowds out docs + backend config).
- **ADR-13 · 2026-07-24 · Nav = glass docked M3 bar · tiles = standard OSM (MVP) · icon deferred.** User approved recommendations. Nav: standard `NavigationBar` geometry wrapped in `GlassSurface` (blur on capable devices, opaque fallback otherwise) — conventional thumb-zone ergonomics under stress. Tiles: plain OSM raster via FMTC cache for MVP; a tile-provider decision (Stadia/Thunderforest/self-hosted Protomaps) is required before real deployment because the public OSM server's usage policy forbids heavy production traffic; muted styling revisited then. Icon: placeholder until Phase 2. _Rejected:_ floating glass pill (eats map space, collides with SOS/sheet zone), style server now (infra before first map render).
- **ADR-18 · 2026-07-25 · Demo Mode (default ON) with an in-memory repository behind a `GroupsRepo` interface.** The app was unevaluable while Supabase anonymous sign-in stayed disabled (user lacked dashboard access), so every screen now runs against local sample data with no backend and no login: groups + chat + members + amenities, verification queue, events. Real and demo repositories implement the same interface, so UI code is identical in both modes and the demo can never silently ship as "the" implementation. Demo chat is NOT encrypted (nothing leaves the device); the E2E path is the Supabase one, reachable by toggling Demo Mode off in Profile. _Rejected:_ faking a signed-in session (would hide real auth failures), shipping screens the user can't open.
- **ADR-17 · 2026-07-25 · No in-app Bluetooth mesh chat.** User agreed. The project's own research (`docs/research/ui-ux-spec.md` Part 3 #7, `group-architecture.md` caveats) flags BLE mesh (Bridgefy) as security-broken (2021/2022 analyses), ~4× battery, and "never for sensitive data"; it also cannot run on the web target. A secure mesh is a multi-month, separately-reviewed effort. _Decision:_ keep it out; revisit only as a dedicated project with an independent security review.
- **ADR-16 · 2026-07-25 · Groups (Phase 3) pulled forward + end-to-end encrypted group chat.** User directed. Stage-1 groups (create/join via expiring code + mandatory approval, members, group-private "amenity" pins, invites) on Supabase with RLS deny-by-default (`supabase/migrations/20260725000002_groups.sql`; `is_group_member`/`is_group_admin` SECURITY DEFINER helpers). **E2E chat** (`core/crypto/`): X25519 device identity (private seed in OS keystore, never uploaded), random 256-bit group key, ECIES sealed-box delivery of the group key to each member on approval, AES-GCM-256 messages — server stores only ciphertext + sealed envelopes + public keys. Sequenced crypto-first (proven by tests) before UI. _Known gaps (logged):_ key rotation on member removal (epoch field present, rotation TBD), local message caching (currently online-fetch), map-picker for group pins, QR invites. _Rejected:_ server-readable chat (privacy), building chat UI before the crypto was tested.
- **ADR-19 · 2026-07-26 · Group chat cached locally as ciphertext, never plaintext; offline sends queue on-device.** Chat was online-fetch only, which broke the non-negotiable offline-first rule during exactly the network conditions the app is built for. Drift schema v2 adds `CachedGroupMessages`, holding the same AES-GCM ciphertext the server holds, keyed by the group key in the OS keystore. Reads are local-first (`GroupsRepo.cachedMessages` paints before any request; `messages` refreshes and throws so the UI can show a visible "Offline — showing saved messages" state instead of an empty chat). Writes encrypt immediately, persist with `pending = true`, and drain oldest-first, stopping at the first failure so ordering can never break; a send with no signal is a success marked "Sending…", not an error. **Caching plaintext was rejected**: the threat model's top row is device seizure, and a plaintext SQLite file would hand an attacker everything E2E encryption was added to protect — with ciphertext, wiping the keystore is sufficient to render the cache unreadable. _Also rejected:_ a stream/Realtime rewrite of the chat interface (larger change, orthogonal to offline), silently swallowing refresh failures (hides degraded state from the user).
- **ADR-23 · 2026-07-26 · Accessibility: automate the colour audit; accept two named colour compromises.** The CVD audit was a recurring manual ritual nobody had run. It is now `test/core/theme/color_accessibility_test.dart`, computing WCAG contrast against both surfaces and simulating deuteranopia/protanopia/tritanopia in CI. It found three genuine contrast failures. **Fixed:** `unverified` #9E9E9E → #616161 (2.61:1 → 6.04:1). **Accepted and pinned, not waived:** (a) `low` amber measures 1.92:1 on the light surface, because every darker amber that clears 3:1 collapses against the red `out` under CVD (#C07000 scores 0.036 separation vs 0.26 today) — "Low vs Out" is the map's most consequential distinction, so separability beats fill contrast; (b) `good` vs `out` collapse under protanopia (0.167), and the only in-family fix makes "good" a teal that collides with the info blue. Both are carried by the standing icon + text rule (WCAG 1.4.1), which is structural here, not per-screen discipline. Measured values are asserted with `closeTo`, so improving the palette *fails* the test and forces a deliberate update rather than silent drift. The test also asserts that the saffron accent is indistinguishable from `low`/`out` under CVD — giving ADR-10's "never use the accent for status" ban actual teeth. _Rejected:_ darkening `low` for a passing number (trades a critical distinction for a metric), recolouring `good` to teal (collides with info blue), waiving the failures with a comment (invisible next time).
- **ADR-22 · 2026-07-26 · Release identity: `io.github.prajwalpatilhub.commonground` + a generated abstract icon.** Reverse-DNS needs a domain the owner actually controls; `io.github.<user>` is the standard convention when there is no custom domain, and is unambiguously theirs. Icon: two overlapping saffron circles with the intersection filled — literally "common ground". Deliberately abstract geometry, because ADR-12 rules out political colour/word signalling and, in this app's context, a recognisable symbol sitting on a home screen is itself a risk to the person carrying the phone. Generated at 1024px with an Android adaptive foreground inside the safe zone; regenerate via `dart run flutter_launcher_icons`. **The applicationId is permanent once published to Play** — change it before first release if the owner registers a domain.
- **ADR-21 · 2026-07-26 · Group broadcasts ride the alerts *presentation*, never the public alerts table.** An admin announcement to a group must not become a row in `public.alerts`: that table is server-readable plaintext and fetchable by non-members, which would undo the E2E model for exactly the most urgent messages. A broadcast is therefore an ordinary encrypted group message whose "broadcast + severity" flag lives **inside the ciphertext** (`GroupMessagePayload`, behind a control-character marker), so the server cannot even distinguish announcements from chatter — metadata minimisation, not just content secrecy. It renders with the alerts severity treatment in the chat and in an Alerts-feed section fed from the local cache, footered "members only" rather than "Verified by admin" so unverified group content is never mistaken for the canonical layer. Untagged text stays a plain message, so pre-existing chat decodes unchanged and no migration was needed. _Rejected:_ a `kind` column on `group_messages` (leaks which messages are announcements), writing to `public.alerts` (breaks the privacy model).
- **ADR-20 · 2026-07-26 · Group-key rotation on member removal, with epochs kept locally.** Removing someone from a group now mints a new random group key at `epoch + 1` and seals it (ECIES) to every remaining **active** member; the removed device is deleted from `group_members` first, so it is never in the recipient set. The client keeps **every epoch it has ever held** in the OS keystore (index at `group_key_epochs_<group>`), and each cached/served message carries its `key_epoch` (Drift v3), so rotation never destroys readable history. A message queued offline before a rotation is decrypted under its old epoch and **re-sealed under the current one before it is sent**, closing the window where a just-removed member could read something typed a minute earlier. Removal is admin-only and enforced server-side (`members_admin_delete`, `envelopes_admin_insert`), with three new pgTAP negatives: a non-admin cannot issue envelopes, cannot remove anyone, and a removed member can no longer read the ciphertext at all. **This is forward secrecy only** and the UI says so: whatever the removed device already downloaded stays on it, and no server-side action can undo that. Members with no published device key cannot be sealed to, so `removeMember` returns that count and the UI warns instead of letting them silently go dark. _Rejected:_ leaving the epoch field unused (a removed member keeps reading everything forever), re-keying without removing first (hands them the new key), deleting old epochs on rotation (destroys the group's own history), per-message ratcheting/MLS (right answer at scale, disproportionate for Stage-1 groups and needs its own security review).
- **ADR-15 · 2026-07-24 · i18n via Flutter gen-l10n (ARB) with bundled Noto fonts; locale persisted, defaults to system.** Typed `AppL10n` from `lib/l10n/*.arb` (en + hi). Noto Sans + Noto Sans Devanagari TTFs bundled as assets (not runtime-fetched — offline-first forbids `google_fonts` network pull), Devanagari set as automatic `fontFamilyFallback` so Hindi renders correct matras/conjuncts. Locale saved in SharedPreferences (non-sensitive; keys/tokens stay in secure storage), instant toggle in Profile. Domain enum labels live in `core/l10n/l10n_labels.dart` (context-based), keeping the presentation `*_visuals.dart` to icons/colors only. _Rejected:_ `google_fonts` runtime fetch (breaks offline), hardcoded strings, storing locale in Drift (overkill).
- **ADR-14 · 2026-07-24 · Sync contract: client-generated ids for idempotency; admin decisions via SECURITY DEFINER RPCs; submissions carry `facility_ref` as text.** Retries after lost ACKs hit a unique constraint on `client_id` and are treated as success (harmless duplicate). Approve/reject are Postgres functions that re-check `is_admin()` from JWT app_metadata, write facilities/capacity/audit_log atomically — no client ever mutates state directly (no UPDATE policy exists). `facility_ref` is text, not an FK, because clients may reference locally-known facilities; the approve function resolves it server-side. _Rejected:_ client-side approve writes (trusts the client), FK on facility_ref (breaks offline-first submissions).
- **ADR-12 · 2026-07-24 · App name = CommonGround.** User's choice. Not site-locked (worldwide roadmap needs no rename), no political color/word signaling, short enough for launcher icons. Dart package stays `jantar_mantar_sahayata`; Android applicationId (`com.example.*`) still to be finalized before store release. - **ADR-24 · 2026-07-27 · Critical-alert signalling: vibration on by default, sound OFF by default, both togglable.** ui-ux-spec §1.10 asks for "optional sound/vibration" on critical alerts. The asymmetry is the decision: a pocketed phone can buzz without telling anyone nearby that its owner is receiving protest alerts, whereas a phone that suddenly chimes in a kettle, a police line or a detention room **identifies the person holding it**. That risk is the user's to accept deliberately, not ours to impose as a default. Implemented with `HapticFeedback` + `SystemSound` from `flutter/services` only — no plugin, no runtime permission, no notification channel, so nothing is added to the permission manifest or the attack surface. Fires **once per alert id** (`CriticalAlertSignaller` keeps the id it has already signalled across rebuilds), so a re-sync, an edit to the same alert, or a widget rebuild stays silent; a genuinely new critical alert signals again. Turning a setting on later does not retroactively buzz for an alert already on screen (`ref.read`, not `watch`). _Rejected:_ `flutter_local_notifications`/FCM push (permission prompt + a server that learns who is online), sound on by default (a safety hazard in the app's own threat model), a long alarm pattern (indistinguishable from a ringtone, same exposure).
- **ADR-25 · 2026-07-27 · Trust scores and promotion, with a verifier that is deliberately NOT a small admin.** Phase 4's purpose is the top live risk in PROJECT_MANAGEMENT.md: verification is a single-admin bottleneck, and during an actual protest a queue nobody drains is the same as no map. `public.user_trust` counts each account's approved/rejected submissions and recomputes a tier (`new` → `trusted` at 5 approvals, → `verifier` at 20) behind an **accuracy gate** — approvals must outnumber rejections 4:1 and 9:1 respectively, so volume alone never buys standing. RLS on the table has **no insert/update/delete policy at all**, so self-promotion is impossible by construction; only the SECURITY DEFINER decision functions write, and every tier change (up or down) is audited. The design decision is how narrow the new role is: a verifier can approve **only updates to facilities that already exist** (never mint a pin on the canonical map), their approvals publish with `verified_at = NULL` — which is exactly what ADR-2's two-axis model is for — they cannot decide their own submissions, they are rate-limited to 30 approvals/hour, and they **cannot reject anything**. Rejection stays admin-only because an approval is self-correcting (the map keeps receiving reports) while a rejection silently removes information from the queue, which is the move a hostile verifier would make. Tiers are recomputed on every decision, so trust is **reversible** without an admin intervening. Thresholds are served by `trust_thresholds()` and rendered from that, so the progress bar can never disagree with the rules the user is judged by. 14 new pgTAP negatives (39 total) prove the narrowness, and were verified to fail when the guards are removed. _Rejected:_ a role claim in JWT app_metadata (server-set, so it would need an admin anyway — the point is automation), letting verifiers create facilities (a fabricated pin is not self-correcting), letting verifiers reject (suppression), latching a tier once earned (an infiltrator builds standing then poisons), computing thresholds client-side (drift).
- **ADR-26 · 2026-07-27 · Corroboration auto-verify, gated on trust and never creditable.** The other half of the bottleneck fix: when several independent reporters agree that a known facility is in the same state, that agreement publishes with no human decision at all (`supabase/migrations/20260727000004_corroboration.sql`, AFTER INSERT trigger). The entire risk is sock puppets — anonymous sign-in is free, so "three users agree" is worth nothing by itself. Three defences, each tested: (1) only submissions from accounts at tier `trusted` or better count, and that tier costs **five admin-approved reports each** to reach, so a quorum of fresh accounts publishes nothing; (2) corroborated approvals **do not credit trust**, or a ring of three trusted accounts could corroborate each other up to verifier and never face an admin again; (3) it can only change the `status` of a facility that already exists and never sets `verified_at`, so the worst case is a status flip on a known pin, corrected by the next report. Agreement is counted over **distinct submitters** (one account filing the same report three times corroborates nothing) within a 20-minute window, and reports that disagree are left in the queue for a human. The audit row carries `actor_id = NULL` and names every submitter, so a colluding ring is visible after the fact — and the app renders that null as "automatic — no admin decision" rather than a blank. _Rejected:_ counting any authenticated user (free sock puppets), crediting trust for corroborated approvals (self-farming ring), allowing corroboration to create facilities (a fabricated pin is not self-correcting), a background job instead of a trigger (a report that publishes minutes later is useless during a protest).
- **ADR-27 · 2026-07-28 · Moderator brake on automatic promotion: a *held* revocation, not just a demotion.** ADR-25 promotes on arithmetic, and arithmetic only demotes an account that gets things **wrong**. It says nothing about one that is accurate and hostile — an infiltrator who reports true facts to build standing and then waits. `revoke_verifier(user, reason)` drops an account to `new` **and sets `held = true`**; the hold is the whole point, because without it the very next approved report would recompute the tier and hand the badge straight back. `bump_trust` keeps counting while held (the record stays honest) but stops re-tiering, and `is_verifier()` returns false for a held account regardless of the tier column. `restore_trust(user)` lifts the hold and **recomputes from the counters** rather than restoring the old badge — after a hold, the record is the source of truth again. Both are admin-only, both are audited with the acting admin, a reason is mandatory on revoke, and an admin cannot revoke themselves. `reporter_history(user)` is **SECURITY INVOKER** on purpose: it only assembles rows the caller can already read, so a verifier calling it gets their own record and an empty list for anyone else — enforced by RLS, not by the screen being hidden. 12 new pgTAP negatives (61 total); the decisive one credits 30 approvals to a held account and asserts it is still `new`, and it goes red when the hold check is removed. _Rejected:_ demotion without a hold (self-reversing within minutes), deleting the trust row (destroys the record and the account simply re-earns it), a JWT-claim-based ban (needs the auth admin API and cannot be done from the app), SECURITY DEFINER on `reporter_history` (would hand every caller everyone's submission history).
- **ADR-28 · 2026-07-28 · Share-my-location: consent screen before the permission prompt; the fix never touches storage.** E7's last item, and the first and only GPS in the app — until now Nearby deliberately worked off the map centre so the binary carried no location permission at all. Adding one is a threat-model change, so the constraints are the feature: (1) a consent sheet states what a single reading does, that anyone it is sent to can see where you are, and that it never reaches our servers — **before** the OS prompt appears, so the prompt is never the first thing the user sees; (2) `Geolocator.getCurrentPosition` only — no position stream, no upgrade from when-in-use to always, and `ACCESS_BACKGROUND_LOCATION` is deliberately absent from the manifest, so the app cannot follow anyone even if compromised; (3) the fix goes to the OS share sheet and nowhere else — never written to Drift, never queued in the outbox, never sent to Supabase, because "don't store precise user location server-side" is not satisfied by "we only keep it briefly"; (4) every use goes through the sheet again — there is no "remember my choice", because a location shared once is not consent to share it later; (5) the link is OpenStreetMap, so the recipient does not have to tell Google where the sender is in order to read the message (ADR-7). A denial or a timeout says "Nothing was shared" explicitly — leaving someone unsure whether their position went out is the worst outcome this screen could produce. _Rejected:_ storing a trusted-contact list (membership metadata we have no need to hold), sending through our own backend (precise location server-side), a background/live-location share (a following device), silently failing on denial.
- **ADR-29 · 2026-07-28 · Ed25519 sender signatures: attribute messages cryptographically, not by the server's word.** Group messages are AES-GCM under a key **shared by the whole group**. That proves a message came from *someone holding the group key* — it does not prove *which member*. Until now the gap was covered by the server: the RLS policy `messages_member_send` enforces `sender_id = auth.uid()` on insert. That is a real control, but it is the server's word, and it is the one guarantee that evaporates the moment the transport is not a server that stamps the sender — precisely the case the offline Wi-Fi analysis targets (`docs/research/offline-wifi-transport.md`). Without it, any group member could originate a message attributed to any other; in this app the plausible attack is a forged "the medical tent has moved" from a trusted organiser. **Each device now publishes an Ed25519 signing key** in `device_keys.signing_public_key` alongside its X25519 identity (two keys because an X25519 key cannot sign, and separate roles mean rotating one does not force the other), and signs a domain-separated blob covering the group id, the key epoch and the whole AEAD box — so a signature cannot be lifted into another group or replayed under another epoch, and `_reseal` re-signs as well as re-encrypts when a queued message crosses a rotation (ADR-20). **The downgrade case is the subtle half:** simply omitting the signature is indistinguishable from an old client *unless* the sender has already published a key — so "no signature from a sender who has one" is treated as **invalid**, while "no signature from a sender with no published key" is merely **unsigned**. Only `invalid` is surfaced in the UI: during rollout most messages are legitimately unverifiable, and warning on all of them would train people to ignore the warning that matters. The column is nullable and no RLS changed — `device_keys` already writes only to `user_id = auth.uid()`, and *that existing rule is what makes signatures mean anything*, since a forged key row would let an attacker sign as its owner (now asserted by three new pgTAP negatives). _Rejected:_ a `sender_sig` column on `group_messages` (the signature belongs inside the envelope so it rides any transport, including a LAN, for free), XEdDSA reuse of the X25519 key (not exposed by the `cryptography` package), signing the plaintext (would require decrypting before you can attribute), warning on every unsigned message during rollout (alarm fatigue), and making signatures mandatory immediately (locks out every installed client).
- **ADR-30 · 2026-07-30 · Sphere/UNHCR adequacy ratios on existing map data, as an indicator that refuses to guess.** July 2026 reporting from the Assam floods described one relief camp of **15,000 people with 6 latrines and 3 hand pumps** and another of **13,000 with 3 latrines** — 2,500 and 4,333 people per latrine against a first-phase emergency maximum of **50** — followed by ~20,000 diarrhoea cases. The failure was not that anyone judged those ratios acceptable; it is that **nobody had the number**. `core/domain/sphere_standards.dart` computes it from data the app already holds: a shelter facility's stated capacity, divided by the usable `toilet` and `water` facilities mapped within 150 m. **No new collection, no schema change, no permission, no personal data** — the whole feature is arithmetic over the existing public map. Four deliberate conservatisms, each tested: (1) a latrine whose status is `out` or `closed` counts as **zero**, because counting broken provision turns a failing camp into a compliant one on paper — the exact failure this exposes; (2) missing data returns `unknown` and renders **nothing**, never "adequate" — silence must not read as a pass; (3) the radius is generous (150 m vs Sphere's 50 m dwelling figure), which over-counts provision and makes the result *less* alarming, the safe direction for a number that accuses someone of failing a standard; (4) the water figure is reported as a **band between the two published thresholds** (250/tap, 500/hand pump) because a facility pin does not record the source type, and a real range beats a confident wrong threshold. The card names the standard next to the ratio and states its own evidence count and that the map is incomplete, so it reads as an indicator rather than an audit. _Rejected:_ a single water threshold (fabricates precision the data model cannot support), claiming litres/person (flow rate is not recorded — the research doc was corrected to match what is actually computable), grading or ranking camps (invites a leaderboard, and §3 of the research bans those on de-anonymisation grounds), and adding new fields to the submit flow to collect latrine counts directly (a data-model and UX change that should be a separate, deliberate decision).
- **ADR-31 · 2026-07-30 · Route hazards as edges, with no way to say a road is open.** The map has only ever held *points*. During the June 2026 Venezuela earthquakes an aftershock collapsed a bridge and cut the parish of Caraballeda off mid-response — a facility pin cannot express "the way there is gone", and this was named in `docs/research/disaster-response-adaptation.md` as the largest genuine model gap. Drift **schema v4** adds `RouteReports`: a single segment (two endpoints), a condition, a cause, and a **mandatory** expiry. Three decisions carry the weight. **(1) There is no `open` condition, and a test asserts the enum stays that way.** Crowd data can report a hazard; it cannot certify that a road is safe, and an app that shows "open" to someone deciding whether to drive into floodwater is making a life-safety claim it has no basis for. `cleared` is the *retraction of an earlier report* — "this was reported blocked and someone has since got through" — rendered thin and dotted so it can never read as a safe-route highlight, and the map carries a note, shown only while hazard lines exist, that an unmarked road has not been checked. **(2) `expiresAt` is not nullable.** A stale blockage is not a harmless leftover: it diverts people away from what may be the only viable road, so every report ages out and has to be re-asserted. The report screen states that reasoning rather than just enforcing it. **(3) A segment, not a polyline or a routable graph** — enough to draw "do not go along here", small enough to sync over a bad link, placeable with two taps one-handed in the rain, which is the actual context. Placement reuses the existing move-the-map-under-a-crosshair pattern, so **no GPS is involved**. Reports are **local-only for now** and the UI says exactly that; a server table, RLS and a verification path are the next step, and claiming "submitted for verification" before that exists would be false. _Rejected:_ an `open`/green rendering (a safety claim we cannot support), a nullable expiry (stale hazards misroute), reusing `FacilityType.danger` as a proxy (a point cannot say which stretch), a polyline editor (unusable one-handed under stress), and syncing before the server side is designed.
- **ADR-32 · 2026-07-30 · "Soft Geometry": adopt the reference's shape language and warm surfaces; never its semantics.** The owner supplied two reference sheets (search-bar shape studies, and app screens in a warm palette) and asked for the app to look like them. Stripped of copy and imagery, the first sheet is a study of a single move — a stadium field with a circular action attached — and five ways of joining the two; the second adds card-per-row, large soft panels, pill CTAs and roughly double the vertical breathing room. All of that is **identity**: it carries no meaning, so it is adopted wholesale and expressed as **tokens** (surface ramp, action tone, radii scale) applied through component themes, so the language holds by construction rather than by per-screen discipline. `NotchedActionField` and `CappedSurface` exist as widgets for the two joins the app actually uses. **What is not adopted is `StatusColors`.** Good / Low / Out / Unverified must stay separable under colour-blindness, and a brown-on-tan monochrome collapses exactly the distinction the map exists for — so they keep the values ADR-23 measured, unchanged. The colour decisions were **measured, not asserted**, and three of them changed as a result: the light sand ground costs about a point of contrast but every swatch still clears 3:1; the warm dark ground `#160F0A` actually *raises* the weakest swatch from 3.00:1 to 3.06:1 versus the old `#141218`; the first clay `#A5713F` matched the reference best but put cream label text at 3.93:1 — under the 4.5 body bar — so it was darkened to `#8C5A29` at the same hue; and dark mode needed an inverted label token, because clay is lighter than the ground there and cream-on-clay measured 2.83:1. The last two were caught by tests, not by eye. **A pre-existing bug surfaced:** `color_accessibility_test.dart` measured against a hardcoded `#FFFBFE`/`#141218` that no screen painted — it now reads `AppTokens` and measures the scaffold, the worse of the two light surfaces. _Rejected:_ adopting the reference palette for status (collapses CVD separation), keeping the original clay (unreadable labels), styling screens individually (drifts), and treating the second sheet's imagery or copy as input at all.
- **ADR-33 · 2026-07-30 · Depth is a contrast fix; the three async states are one decision.** Auditing the app against the same method used on the reference images turned up two classes of gap. **First, depth.** Soft Geometry (ADR-32) is tone-on-tone, and tone-on-tone measures badly: a shell card on the sand scaffold is **1.15:1** (dark 1.11:1), well under the 3:1 WCAG 1.4.11 asks of a UI component boundary. That is a legibility regression ADR-32 introduced, so depth here is not decoration — it is the only thing making a card perceptible as a card. Two mechanisms, because one is not enough: a **warm-tinted shadow** (a grey shadow on a warm ground reads muddy) and a **hairline that clears 3:1 against both the card and the ground**, which is what carries the boundary in direct sunlight and on the no-blur outdoor path where a soft shadow is simply not visible. Both numbers are pinned in the contrast test so neither gets tidied away as ornament. **Second, the async states.** A count across all 21 screens found empty rendered as a lone centred sentence, loading as a spinner on a blank screen — indistinguishable from a broken screen, and on a bad connection that ambiguity lasts a long time — and error as `'$e'` printed verbatim, which tells a volunteer in a field nothing and shows Postgres internals to anyone reading over their shoulder. `EmptyStateView` / `LoadingStateView` / `ErrorStateView` replace all three; the error view keeps the raw exception behind a disclosure rather than discarding it, so debugging still works. The skeleton holds still under `MediaQuery.disableAnimations`, which covers both reduced-motion and Android battery saver. **Third, offline.** The app has been offline-first since E2 and the only place that said so was group chat — a frozen map and a live map looked identical. `OfflineBanner` sits above every tab, driven by **whether the backend actually answered** (`SyncService.reachable`) rather than by a connectivity plugin: "the radio says Wi-Fi" and "our backend answered" are different facts that disagree during exactly the internet shutdown this app is built for, and it adds no Android permission. Unknown reads as online, so nothing claims staleness before the first cycle has run. _Also fixed:_ the skeleton's stagger used a bare `Future.delayed`, which leaked a pending timer past dispose and failed teardown in every widget test that mounted a loading screen — now a cancellable `Timer`. _Rejected:_ elevation by tone step alone (measured 1.15:1), a connectivity plugin (wrong fact, new permission), discarding exception text entirely (kills debugging), and an always-visible offline chip (offline is the expected condition here, not an error).
- **ADR-34 · 2026-07-30 · Automate the accessibility audit, and let it find things.** ADR-23 automated the colour half of the audit because "a recurring manual ritual nobody had run" is not a control. The interaction half was still manual, and the codebase showed it: `FocusNode` appeared **zero** times and `Semantics` in four files. Flutter ships three guideline matchers — `androidTapTargetGuideline`, `labeledTapTargetGuideline`, `textContrastGuideline` — and this project ran none of them. They now run over eight real screens in CI. The contrast one is worth having *alongside* ADR-23 rather than instead of it: that test measures swatches in isolation, this measures what a pixel actually becomes after theme, opacity and stacking. **It found two real defects on the first run.** (1) **The SOS hero was broken on small phones.** It was `FittedBox(scaleDown)` around a fixed 220 px disc taking whatever height the fixed chrome left over — which at 360×640, a device CLAUDE.md names as an explicit target, **overflowed outright** with no measurable disc, and the FittedBox hid that by scaling the hero away. Measured diameters before → after: 360×640 overflow → 220; 390×844 165 → 220; 800×600 41 → 212. The app's single most important button was in practice unusable on a small screen. Fixed by inverting the layout priority: the hero takes a guaranteed 42% of the body height (bounded 112–260) and the *secondary* call tiles scroll instead. The hero is deliberately **not** inside a scroll view — an emergency control has to be where it was last time, and a scrollable ancestor also joins the gesture arena and swallows the hold, which is how the first attempted fix was caught. A test now pins the disc at three real device sizes. (2) **The map was an unlabelled interactive region** on every screen carrying one, so a screen reader announced an unnamed control in the middle of the screen. **Visible focus** was added at the same time (WCAG 2.4.7): a saffron ring resolved per-state through the button themes, saffron because ADR-10 forbids the accent from conveying status so it cannot be confused with good/low/out, and because it holds up on both grounds. Plus pull-to-refresh on the admin lists, with the AppBar button kept for anyone who cannot perform a pull gesture. _Rejected:_ fixing the SOS hero by scrolling it (moves an emergency control and breaks the hold gesture), lowering the tap-target floor to make the test pass, and asserting the focus ring by reading the theme map only — the test resolves what the buttons actually inherit and presses Tab for real. _Still manual, still on the board:_ TalkBack/VoiceOver traversal **order** on real OEM devices. A label existing is not the same as a sensible reading order, and no matcher checks that.
- **ADR-35 · 2026-07-30 · Status colour reaches the screen through the token, or it does not reach the screen.** Six places painted a status colour as a copied hex instead of reading `StatusColors`: the pending-submission pin, three event states, the map SOS button and the queue's approve/reject buttons. Each rendered correctly on the day it was written, which is exactly the problem — a literal that equals the token is invisible to every test, and then the token gets corrected and the literal does not follow. **`PendingMarker` proved it.** It painted `#9E9E9E`, the precise grey `StatusColors` had abandoned for measuring under 3:1; the token was corrected twice and the pin moved neither time, and the contrast suite could not see it because the suite measures tokens and the pin was not using one. Measured today that grey is **2.43:1** against the light card. Three things changed. (1) **Every literal now goes through the token**, including the SOS screen — which reads `StatusColors.standard.out` off the constant rather than off the theme, so it honours the token while staying deliberately theme-independent. (2) **A source scan fails the build if a status hex reappears** anywhere outside `status_colors.dart` and `alert_visuals.dart`, and it also refuses the two retired greys outright. A source scan rather than a widget test because no widget test can see this bug class. (3) **The contrast suite now measures all four painted grounds, not two.** It measured the scaffolds only, reasoning that the scaffold is "the darker of the two on light and therefore the worst case" — true on light, **false on dark**, where the card is the lighter ground, and a map pin paints its glyph on the card. That untested ground was carrying most of the status colour in the app, and measuring it found `unverified` at **2.75:1 on the dark card** while passing 3.06:1 on the dark scaffold. `unverified` moves `#616161` → **`#767472`**, the one value clearing 3:1 on all four grounds (worst 3.66:1) while *improving* CVD separation from the other statuses, 0.183 → 0.248; warm-biased rather than pure grey so it sits inside the Soft Geometry ramp. The same pass routed the hand-rolled radii through `AppTokens`: alert and broadcast cards had overridden the themed shape to carry a severity border and silently taken the radius with it, rendering at 12 while every other card rendered at 22. Chat bubbles get named tokens (`radiusBubble` 16, `radiusBubbleTail` 5) and the speaker-side tail from the approved wireframe, mirrored for RTL — so which side a message came from survives without relying on fill colour, the same principle as status never being colour alone. Nine test files were building a `MaterialApp` with **no theme**, rendering a tree that does not ship; `testAppTheme()` in the harness fixes that, and one test that had hand-rolled a `ThemeData` carrying only the extension no longer needs the workaround. _Rejected:_ leaving the literals because they currently match (that is the bug, not a mitigation); a lint rule instead of a test (the allowlist needs to be reviewable in one place); and keeping `#616161` and exempting the dark card the way `low` is exempted — `low`'s exemption is bought with a documented CVD trade-off that has no equivalent here, a legible grey simply exists. _Still open:_ map markers and the SOS screen keep their own radii on purpose; both are deliberate vocabularies rather than drift, and neither is covered by the shape test.
- **ADR-36 · 2026-07-30 · Nobody joins a group from the client.** The policy `members_self_join ... with check (user_id = auth.uid())` constrained one column. `role` and `state` have safe defaults, but **a column default only applies to an OMITTED column** — an attacker supplies them. So `POST /rest/v1/group_members {group_id, user_id: self, role: "admin", state: "active"}` passed the check and made the caller an active admin of any group whose id they knew, and `groups_read` makes every `visibility='public'` id enumerable. Reachable by anyone: the publishable key ships in the web bundle by design, the app signs in anonymously by itself, and an anonymous Supabase session carries the **`authenticated`** role — `to authenticated` is not a barrier. E2E encryption held (no envelope sealed to the attacker's X25519 key, so message bodies stayed unreadable) but everything around it did not: the member roster, the group's real-world pin coordinates, live invite codes, group rename and member deletion. For a protest app the roster *is* the sensitive data. **Fixed by removing client INSERT on `group_members` entirely** rather than narrowing the policy: creation seeds the creator through an AFTER INSERT trigger on `groups`, and joining goes through a SECURITY DEFINER `join_by_invite()` that validates the code, writes a `pending` row and spends the invite use atomically. _Rejected:_ narrowing the WITH CHECK to `role='member' and state='pending'` — that leaves a policy whose correctness depends on enumerating every column an attacker must not set, so the next column added to the table silently reopens it. _Why the old suite missed it:_ it only tested the READ policies ("an outsider cannot read group X") and never the write that turns an outsider into an insider. 16 new assertions attack the membership write itself, and mutation-testing them by restoring the old policy turns the roster/pins/invite-code assertions red — the exploit demonstrated, not just asserted.
- **ADR-37 · 2026-07-30 · The web build is self-contained, and says how wide it is.** Three defects in one 40-line file. (1) **`web/index.html` had no `<meta name="viewport">` at all.** Measured on an emulated iPhone 13 (390 css px): the app laid out at **980 css px** because that is mobile Safari's fallback, so every responsive breakpoint tuned in ADR-34 was evaluated against a viewport the device does not have — and without `user-scalable=no` a pinch is a *browser page-zoom*, not a map gesture, which is the reported "the map disappears when I zoom in or out". Measured again after the fix: 390 px. (2) **CanvasKit was fetched from `www.gstatic.com` at runtime**, so the app would not start at all when Google is unreachable — the exact network conditions this app exists for — and every cold load announced a visitor to a third party. Now built with `--no-web-resources-cdn`; CI asserts the `useLocalCanvasKit` flag rather than grepping for the string, which is a false positive because the CDN URL survives as the untaken branch. (3) **No CSP.** GitHub Pages cannot set response headers, so a meta CSP is the only egress control the deployment has; `connect-src` pins network egress to the tile server and this project's own Supabase host. It immediately caught a leak nothing else had found: the app also pulled **Roboto from `fonts.gstatic.com`** on every load despite bundling Noto Sans. Blocked, and verified the app still renders correctly with the bundled fonts. _Rejected:_ allowing `fonts.gstatic.com` (the fonts are already in the bundle); relying on the CI check alone (a Dart test asserts the same invariants locally, reading `SupabaseConfig.url` and `MapConfig.urlTemplate` instead of a second copy of the URLs, because a stale allowlist fails silently as "sync is just slow").
- **ADR-38 · 2026-07-30 · Demo Mode announces itself on every screen.** Demo Mode defaults ON (ADR-18) and the hosted build is public, so every visitor saw fabricated relief camps, capacity counts, alerts and an admin verification queue — with nothing on screen saying so except a toggle two taps into Profile. For a map people may use to decide where to walk for water, an unlabelled simulation is a safety problem rather than a UX one, and a screenshot of it is indistinguishable from real reporting — precisely the fabricated-data vector the disaster research told us not to create. A persistent, non-dismissible banner now sits above every tab, ranked *above* the offline strip: "this is not real" outranks "this may be old". Deliberately louder than `OfflineBanner` (warning tone, icon + text, never colour alone) because offline is the expected condition this app is built for and fabricated data is not. _Rejected:_ making it dismissible (a dismissed warning on a screenshot is no warning at all) and defaulting Demo Mode off (it is what makes the app explorable with no backend — the fix is labelling, not removal). A test pins that the banner disappears entirely once Demo Mode is off: warning on real data would train people to ignore it.
